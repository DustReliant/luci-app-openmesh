# OpenMesh Manager 开发工作流规范

> 本文件是全项目的开发宪法。每个模块开工前必读，每个 PR 必须符合本规范。

## 1. 项目阶段总览

```
OpenMesh Manager
│
├── 01 项目调研                ← docs/research/
│   ├── mesh11sd（能力边界、UCI 全量选项、局限）
│   ├── luci-app-easymesh 系列（实现方式盘点、空白点确认）
│   ├── OMM / and-elf（功能架构对比、避免重蹈的坑）
│   ├── OpenWrt 版本兼容性（hostapd-ubus / iwinfo-json / netifd 差异采样）
│   └── 加密库选型（libsodium vs mbedtls 3.6，ADR-0004）
│
├── 02 技术架构                ← docs/architecture.md + docs/design/
│   ├── daemon（openmeshd 模块划分、资源预算）
│   ├── ubus API（方法/事件表、ACL）
│   ├── UCI（/etc/config/openmesh 全量 schema）
│   ├── 节点发现（UDP 签名广播，ADR-0003）
│   └── 节点认证（身份/领养/会话加密/replay 防护，ADR-0004）
│
├── 03 Mesh 核心               ← V0.2 主体
│   ├── 802.11s（V0.1 即含原生 UCI 静态配置，ADR-0006）
│   ├── batman-adv（feeds/routing，模式 B 默认，ADR-0002）
│   ├── 有线回程 / 无线回程 / 自动选择（全部依赖原生 metric，不自研切换）
│   └── Backhaul 故障切换（验证与展示，非自研）
│
├── 04 LuCI                    ← V0.1 起
│   ├── 首页（节点表 + 待领养横幅）
│   ├── 节点管理（领养/改名/移除）
│   ├── 拓扑图（自绘 SVG，按跳数分层，禁引重型图库）
│   └── 节点详情 / 建网入网向导
│
├── 05 自动化                  ← V0.2–V0.4 递进
│   ├── 自动发现（V0.1）/ 自动领养确认流（V0.1）
│   ├── 回程自动选择（V0.2，batman-adv 原生）
│   └── 故障检测与自动恢复（V0.4，事务回滚在 V0.1 即内置）
│
├── 06 测试                    ← docs/testing/
│   ├── CI：{23.05, 24.10, master} × {x86_64, mediatek/filogic} SDK 矩阵
│   ├── 单元（宿主机 x86 直跑 daemon 模块）
│   ├── 集成（loopback 双进程 → QEMU 多 VM）
│   └── 真机（2×AX3000T/MT7981 + 1×MT7986，多节点联调）
│
└── 07 发布                    ← V0.1 后启动
    ├── GitHub（README/声明/License）
    ├── OpenWrt package（feeds 提交策略：先独立 feed，后官方）
    └── Release（ipk 产物 + 固件集成 seed 配置）
```

**阶段纪律：不跨越多个阶段。** 任何时刻只推进一个里程碑（M0–M8，见 `roadmap.md`）；下一版本的任务拆解必须等当前版本出口条件全部达成后再做。

## 2. 开发循环（每个功能模块必须完整走一遍）

```
分析 → 设计 → 小范围实现 → 编译 → 测试 → 修复 → 重构 → 文档 → Git commit
```

每步准出标准：

| 步骤 | 准出标准 |
|---|---|
| 分析 | 回答完「开工前 10 问」（§3），写入 `docs/design/<模块>.md` |
| 设计 | 接口、数据结构、错误路径、超时、资源预算全部落纸；不确定的 API 列入「待验证清单」 |
| 小范围实现 | 单次改动聚焦单一模块；不夹带顺手重构 |
| 编译 | 本地 24.10 SDK 编译零警告（`-Wall -Wextra`）；CI 三版本矩阵全绿 |
| 测试 | 模块 DoD 中的测试项全部通过；失败即修，禁止跳过登记 |
| 修复 | 已知缺陷清零，或转为带复现步骤的 issue |
| 重构 | 无 TODO/伪代码冒充实现；命名与既有代码一致 |
| 文档 | 模块设计文档、`architecture.md`、ADR（如决策变化）同步更新 |
| Git commit | 单一主题、约定式消息（§6） |

## 3. 开工前 10 问（强制，答案写入模块设计文档）

1. 当前功能解决什么问题？
2. OpenWrt 原生是否已经提供相关能力？
3. 是否存在成熟开源项目可以复用？
4. 为什么需要自己开发？
5. 模块与其他模块如何交互？
6. 配置保存在哪里？（持久化 / 重启后如何恢复）
7. ubus API 如何设计？（方法、参数、返回、ACL）
8. 出错以后如何恢复？（超时、回滚、崩溃、掉电）
9. 如何测试？（DoD 可执行断言）
10. 如何兼容不同 OpenWrt 版本？（差异点与退化策略）

## 4. 模块完成报告模板（每模块交付时输出）

```markdown
【本次完成】一句话说清交付了什么能力
【修改文件】新增/修改/删除的文件清单（含行数）
【核心设计】关键决策、接口、数据结构（可引用 docs/design/<模块>.md）
【代码】关键代码段的落点（文件:行号）；不粘贴整文件
【编译方法】确切的命令序列（SDK 路径、make 目标）
【测试方法】确切的命令序列 + 预期输出（可复制执行）
【已知问题】明确列出；不允许隐藏
【下一步】下一个模块编号与一句话范围
```

## 5. 阶段门槛（Stage Gates）

| 门槛 | 出口条件（全部满足才进入下一版本） |
|---|---|
| V0.1 → V0.2 | M0–M8 全部 DoD 达成；2 节点真机端到端：发现→领养→建网→拓扑；回滚机制演练通过 |
| V0.2 → V0.3 | 有线+无线混合回程真机运行 72h 无人工干预；batman-adv 切换可观测 |
| V0.3 → V0.4 | k/v/r 在 ≥2 台设备生效并捕获漫游事件 |
| V0.4 → V1.0 | 故障注入测试（拔线/杀进程/断电）全部自动恢复 |

## 6. Git 约定

- 分支：`feat/m<N>-<slug>`、`fix/m<N>-<slug>`、`docs/<slug>`
- commit 前缀：`feat: / fix: / docs: / test: / refactor: / chore:`，一行 ≤ 50 字符 + 正文说明动机
- 一个模块 = 一个分支 = 若干小 commit；合并前 squash 或保留均可，但主题必须单一
- 主分支 `main` 始终可编译（CI 门禁）

## 7. 硬性检查清单（PR 自查，违反即打回）

### 代码
- [ ] 实际可编译，无伪代码、无省略关键路径
- [ ] 未凭记忆假设 OpenWrt API；不确定处已在文档「待验证清单」标注并核实
- [ ] 所有配置考虑重启持久化；daemon 考虑异常退出（procd respawn）
- [ ] 所有网络通信有超时；所有节点通信有认证
- [ ] 单节点异常不会拖垮 daemon（输入防御校验 + per-peer 隔离）

### 安全
- [ ] LAN 不可信假设成立；新消息类型必须有 nonce/counter 与 replay 窗口
- [ ] 未领养节点不接受任何配置类消息；密钥文件权限 0600

### 资源
- [ ] 二进制 �� 150KB、RSS ≤ 3MB、announce ≤ 512B、state.json ≤ 32KB（CI 冒烟断言）
- [ ] 不引入庞大依赖；新增依赖必须先立 ADR

### 兼容
- [ ] 版本差异代码集中在 `compat.h/compat.c`；端口名从 `board.json`/ubus 动态获取，禁止硬编码
- [ ] CI 三版本矩阵全绿

## 8. 文档维护规则

- `architecture.md`：总体架构，版本化（v1 草案 → 评审 → 冻结；改动走 PR）
- `decisions/NNNN-*.md`：ADR，一经接受不修改内容，推翻靠新 ADR 引用旧 ADR
- `design/<模块>.md`：每个模块一份，含「开工前 10 问」答案，实现完成后回填实际接口
- `research/*.md`：调研结论必须附证据（源码路径 / commit / 实测输出），禁止只写印象
