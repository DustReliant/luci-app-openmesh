## batman-adv 接口实证（2026-10-24，feeds/routing/batman-adv）

- netifd proto `batadv`：软接口（`config interface 'bat0'` + `option proto 'batadv'`，参数 aggregated_ogms/bonding/gw_mode 等）。
- netifd proto `batadv_hardif`：参数 `master`（bat0）、elp_interval/hop_penalty/throughput_override；设备由 wifi-iface 的 `network=` 引到本 section，setup 即 `batctl meshif master interface add`。
- 包内无 /etc/config/batman-adv 初始文件（内核参数经 proto 选项即全）。
- 模式 B 产出组合：wireless（mesh iface 挂 om_mesh）+ network（bat0 + om_mesh + br-lan ports 追加 bat0）——**netconf 事务必须双文件快照**。

## 断连安全（M9 真机验证设计）

模式 B 改造 br-lan，验证期间 SSH 可能中断 ≤30s（自动回滚恢复）。演练脚本必须 nohup 本地运行、结果落盘，SSH 重连后取报告；回滚由 daemon 内部定时器保证，与 SSH 无关。

## M9 实现后回填（2026-10-23/24）

- 真机 DRILL-OK（r11）：hybrid 应用（om_bat UP + mesh 挂载 batman）→ 30s 自动回滚（wireless+network 双文件复原）→ 确认保留 → 清理复原。
- 踩坑三则：
  1. **netifd 只在启动时扫描 /lib/netifd/proto/**——运行期安装的 batadv proto 脚本不被识别（新装 kmod 的设备需一次 network restart；预装固件无此问题）。
  2. **回滚竞态防御**：曾出现回滚后 om wifi 段残留（外部写回竞争，快照链被污染后逐代继承）→ r11 起回滚在文件恢复后强制 purge_om_sections()（om 段无条件属于本项目，删除恒安全）。
  3. **section 删除不带走 device 段 ports 列表项**——清理时需显式 del_list。
- gen_key 修复后的密钥已验证无周期模式（dcb6gka6fgab 等）。
- 边界：双机 hybrid 对传（真 originator/选路数据）待第二台设备。

## r19 双机无线 mesh 打通（2026-10-25，项目首次真实 802.11s 链路）

**结果：控制器 AX3000T ↔ x86 代理（rtl8188ee）双机 802.11s + SAE 链路建立**：控制器侧 -27 dBm / 代理侧 -12 dBm（同屋近距离），代理 PHY 72.2 Mbps（MCS7 short GI，1x1 HT20 满血），mesh0 桥入 br-lan 转发；`get_links` 返回真实 peer/RSSI 且 MAC 与 announce 绑定成功——**M15 Mesh 拓扑页真数据闭环**。

本轮排障链（每条都是真机才暴露的）：

1. **rtl8188ee 驱动三件套补丁**（scripts/openwrt-patches/）：PKG_DRIVERS 加回 + KernelPackage 定义 + **RTL_CARDS menuconfig 总门**（不开它 kconfig 静默丢弃全部 rtlwifi 符号）。内核 6.6 + backports 6.12.96 组合首验通过（rtlwifi 源码在 backports 里一直完整，301 文件）。
2. **x86 内核缺 CONFIG_CRYPTO_CMAC**：MAC80211 的 kconfig 硬依赖（mediatek 显式有、x86 从来没有）——缺它则 MAC80211 永远无法启用且零报错。=m 模块形态 + 设备侧装 kmod-crypto-cmac 解决。**内核配置哈希随配置变化**：改内核配置后 kmod 依赖哈希失配，需连 kernel 包一起装或 --force-depends。
3. **控制器固件是 wpad-basic（无 mesh 能力）**：mesh0 接口能建但 mesh 组永远不 join——**M7/M9 单机演练的"mesh up"只是接口层面，入组从未成功过**（单机无法察觉的盲区）。换 wpad-mesh-mbedtls（官方 24.10.2 同版本号 ipk 直接可用）；换包后必须 kill 旧 wpa_supplicant 让 netifd 用新二进制重生，立即 MESH-GROUP-STARTED → 秒级配对。
4. **M11 mesh peer 解析器格式不符**：24.10 的 iwinfo 对 mesh peer 输出与 AP 客户端相同的紧凑单行格式，M11 按旧"逐字段行"格式写的解析从未见过真数据——已统一为紧凑格式。另发现 **daemon 内 popen 管道读 iwinfo 偶发零输出**（交互执行正常、daemon 环境复现也正常，机理未明）——采集改为输出落 /tmp 文件再读，稳。
5. **会话层两个新 bug（待修，记 M17）**：①代理会话每 ~20s 断链重拨（36+ 次复现，疑 KA 超时参数）；②mesh_create 的 CONFIG 推送不能送达代理（疑与①相关，推送仅发 PS_ESTABLISHED peer）。本轮代理侧 mesh 为 SSH 手工配置等价落盘。
6. 杂项：mesh_create 每次不传 key 会生成新密钥（多次 push 后代理侧密钥需对齐最后一次）；announce 的 MAC 采样在启动时（mesh0 后出需重启 daemon 重采）；agent 按 ADR 设计不注册 ubus（控制器专属 RPC）；x86 软重启必挂死（两次复现，只能断电）。

**下一步**：修会话两 bug（M17）→ mesh_create 全自动双机复验 → V0.2 hybrid 模式 B 双机 → 72h 稳测。

## r18 双机开张（2026-10-25，控制器 AX3000T + x86 代理，V0.2 关键节点）

**控制面真机双机全通**：发现 → 会话 → 领养 → 持久化 → 重连，全链路首次在两台物理设备间跑通。

- **入网对象**：x86（AMI Aptio CRB，RTL8188EE 2.4G 网卡，8G 内存）刷 24.10 种子镜像（含 files 覆盖：公钥 + 节点首启哑 AP 化脚本，工作完美），静态租约 192.168.40.232。
- **发现**：announce 10s 周期，控制器 pending 列表即时出现代理（model/fw/addr 全字段正确）。
- **领养**：`role=auto` 双方都自封控制器（auto=无 controller_addr 即控制器）→ 代理显式 `role='agent'`+`controller_addr` 后拨入；GRANT 需 `join_open=1` 配对窗口（M4 设计如此，首次配对后关闭）。
- **M4/M5 真机回归 ✓**：代理关 join_open 重启 → 同 node_id → WELCOME 重连成功；`list_adopted` 首次出现 `online: true` 的真实节点。
- **建网（半成）**：`mesh_create band=2g`（代理只有 2.4G）→ 控制器 mesh0 起来（phy0-mesh0，信道 1 HT20，事务确认提交）；配置经会话推抵代理（"mesh config received"），但代理报 `no radio for band '2g'`——种子镜像没带无线驱动。

**发现的真实问题（后续任务）**：
1. **rtl8188ee 在本 24.10 快照不可编**：mac80211（backports 6.12.96）PKG_DRIVERS 已剔除 rtlwifi 家族（旧 23.05 树才有）。无线 mesh 节点首选改 **小米 4A**（mt7621+mt7603/mt7612，mt76 原生支持），需编 ramips/mt7621 种子；rtl8188 补丁加回作备选路线。
2. **发现协议自回声 bug**：代理三次把**自己的广播**记为 new node（同 id 同 addr）——discovery.c 自过滤逻辑待查修。
3. 硬件运维教训入 DEVICE-CREDENTIALS.md（仓库外）：未知网段设备的万能入口=IPv6 链路本地；精简系统无 nohup 时 sysupgrade 用前台直跑；x86 刷机后重启环节挂死 40min → 手动断电恢复成功（镜像已写完）。

**下一步**：4A 种子构建（无线 mesh 节点）→ 双机 802.11s 真链路 → M15 Mesh 拓扑真数据 → V0.2 hybrid 72h 稳测。

## M17 会话层两 bug 修复（2026-10-25，r19 补遗）

**M17-a：代理会话 20 秒断链**——根因：代理侧 GRANT/WELCOME 两处 `PS_ESTABLISHED` 转换都没有重挂 `p->timer`，连接时挂的 `agent_hs_timer_cb`（10s 握手超时）在链路建立 10 秒后照常触发杀链，退避 10 秒重拨 → 恒定 20 秒循环（控制器侧 `ctrl_peer_online` 当年有正确重挂，代理侧漏了同款）。修复：新增 `agent_ka_timer_cb`（对齐控制器语义：非 ESTABLISHED 或 last_rx 超 OM_KA_DEAD=45s 判死）+ 两处转换后 cancel/重挂 15s。真机验证：修复后 2 分 12 秒零重连、单条 TCP 持续 ESTABLISHED、`online: true` 稳定。

**M17-b：CONFIG 推送不达**——与 a 同根（断链循环下 peer 状态/计数不可靠）。a 修复后真机验证：`mesh_create` → 会话推送 → 代理 "netconf applied (gen 1)" → **代理自动确认（会话流量即存活证明的设计首次真机生效）** → 双侧提交，mesh 无感延续（-27 dBm）。**全自动建网管线自此完整可用。**

遗留（不阻塞）：向导页 mesh_create 默认 5G 的交互缺陷；回滚 purge om 段不保护已提交配置（见 r19 节插曲）；daemon 内 popen 读 iwinfo 偶发零输出机理未明（已用落文件方案规避）。

## r20 hybrid 模式 B 双机全自动 + 正式 72h 稳测开跑（2026-10-25）

**hybrid 双机一条命令全自动完成**：`mesh_create mode=hybrid` → 双端 om_bat UP、mesh 硬接口挂载（phy0-mesh0 master om_bat）、br-lan 端口并入、**batman originators 互见**（直连 TQ 229）。代理 1 秒级收到推送并自动提交——全自动管线在 hybrid 形态同样成立。V0.2 出口条件"batman-adv 切换可观测"达成。

**M9 originators 解析器三连坑（全部修复）**：
1. batman-adv 2024.3 行格式与 M9 时代完全不同（" * MAC last-seen (TQ) NEXTHOP [IF]"）；
2. 数据行行首是"空格+星号"，星号剥离最初只查了第 0 位；
3. **%15s 写入 q[8] 缓冲区溢出**（"phy0-mesh0" 10 字节）→ 栈破坏导致解析静默失效——本日最隐蔽一坑。
另：batctl 采集同样改落文件（daemon 内 popen 偶发零输出的通用规避）；前端 bindLinks 改大小写不敏感（iwinfo 输出大写、batctl/announce 小写，原字符串精确比较会让同链路一半绑定一半游离）。

**踩坑**：代理侧早前手工建的 wifi-iface 段与 netconf 推送段并存，导致 mesh 硬接口未挂载 batman——删手工段即愈。教训：手工应急配置在正式管线接手时必须清理。

**正式 72h 稳测**：2026-10-25 13:30 UTC 起（hybrid 形态、单采样器 60s/行：uptime/节点/在线/RSS）。通过即打 v0.2 正式 tag。
