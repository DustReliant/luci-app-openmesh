# M23 LAN 口自动识别与自动接入（Phase 6.4 / 7.x 收官）

状态：已实现（2026-11-11；C 68 项 + JS 25 项 + 全套回归全绿，SDK 零警告 ipk r25。ingress 归属与自动接入的**真机行为 NOT TESTED**——设备不可达；discovery 213 项宿主回归证明协议层无回归）

## 开工前 10 问（摘要）

1. **解决**：m19 既定路线"检测到对方也是 mesh 设备自动组网"——网线插上后无需手工选口，系统识别对端并提示/自动接入。
2. **原生**：无现成方案；识别信号选 **discovery announce 的 ingress 归属**（备选 batman OGM 更复杂且要求 batman 已在跑，弃）。
3. **复用**：既有 UDP 签名 announce（防伪造/防重放不变）、m21 端口分类器、m22 port_apply 事务底座、保护口咽喉点。
4. **自研**：接收路径 IP_PKTINFO/recvmsg 取 ingress 接口 + 提示表 + 稳定性判定 + 自动接入引擎。
5. **交互**：announce 从物理口进入 → 提示表计数 → 稳定（连续 2 次，约 20s）→ 提示进 ports API（向导显示"检测到 mesh 对端"）；自动模式开启时 → 引擎按门禁接入。
6. **存储**：提示表纯内存（进程重启重新学习，20s 即恢复）；自动模式开关 `openmesh.main.wired_auto`（默认关，向导 UI 持久化）。
7. **ubus**：无新方法；`ports`/`port_plan` 回复新增 `mesh_peer`/`mesh_peer_stable`（有近期提示时）。
8. **恢复**：自动接入走 30s 事务（不确认即回滚）；carrier 消失只影响提示新鲜度（35s 过期），**不自动回退已接入口**（防插拔抖动反复事务，m19 既定）；对端换设备时计数重置重新判定。
9. **测试**：om_autojoin_should 纯门禁 7 项（含 mgmt_unknown 永不自动接入）；JS 5 项（标签/UCI 持久化/源级契约）；discovery 213 项回归。
10. **兼容**：IP_PKTINFO 失败则无提示功能但发现协议照常；代理端照常收 announce（提示只在控制器消费）。

## 关键设计决定

- **识别原理**：同节点的 announce 既经无线 mesh（ingress=phy\*-mesh0/om_bat，被前缀过滤排除）也可能经网线直连（ingress=物理口）到达——只有**签名验证通过**且 ingress 为物理口的包才记提示；表按口一行、最多 8 行、淘汰最旧。
- **稳定性防抖**：连续 2 次（≈20s）才算稳定提示；同口出现不同 node_id 时计数重置（换设备场景）。回调只在"达到 2 次"的瞬间触发一次。
- **自动接入 = 手动减去风险**：`om_autojoin_should` 要求 全开/稳定/有 mesh/无活动事务/**verdict 严格 eligible**——mgmt_unknown（唯一可人工确认翻越的风险）在自动路径**永不可过**；保护口/WAN/VLAN/DSA-CPU 因 verdict 不 eligible 同样被挡；接入动作复用 mesh_apply 事务（30s 回滚 + 快照）+ 保护口咽喉点 + 代理推送。
- **默认安全**：wired_auto 默认关闭——不开启时自动识别只做**提示**（向导信息面板绿字"检测到 mesh 对端·稳定/识别中"），绝不动作。
- **无提示风暴**：口接入成为 batman 硬接口后，对端广播经 batman 封装到达（ingress=om_bat 被过滤）→ 提示自然停止，无循环。

## 已知边界 / 后续

- ingress 归属（IP_PKTINFO/recvmsg/if_indextoname）与自动接入引擎的真机行为 NOT TESTED（设备不可达）——待 x86 接回后：插线 → 35s 内观察 ports API 的 mesh_peer → 开自动模式 → 验证自动事务。
- 提示不区分"已领养/未领养"对端（都提示）；自动接入不校验对端是否已领养（mesh_apply 本就无害——对端若非 mesh 成员则链路不建立、30s 后回滚）。收紧为"仅已领养对端自动接入"是后续一行门禁的事，按真机观察决定。
- 广播经中间交换机转发的场景（对端隔着交换机）也会产生提示——分类器无从分辨直连/经交换，符合"该口确实通向 mesh 设备"的语义。
